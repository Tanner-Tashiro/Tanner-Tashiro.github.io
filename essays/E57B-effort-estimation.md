## How Did I make Effort Estimations
I made my effort estimates primarily based on my perceived complexity of each task and by comparing tasks to similar work I had done earlier in the project. For example, when estimating the “Create Listing Page” and “Create Study Groups Page,” I considered both to be full page implementations involving UI layout and some level of data handling, so I estimated them in the range of 150–180 minutes. Additionally, I thought to myself that these 2 tasks would be relatively similar since they are kind of following the same structure, but I would later encounter some differences that would be somewhat problematic. For smaller tasks like “Updating the Landing Page,” I had already had practice with styling, so I estimated less time (around 60 minutes) because it involved reusable UI elements and less logic.

I did not have formal historical data at the beginning, but as the project progressed, I started using my previous issues as reference points. For instance, if a prior page took around 140 minutes of coding effort, I would base new estimates for similar pages slightly above or below that depending on the complexity.

## Did estimating in advance provide any benefit?
Even though many of my estimates were inaccurate, estimating in advance was still helpful for planning and prioritization. It gave me a rough idea of how much work was required for and issue and helped me decide which tasks to start earlier. For example, I initially underestimated the “Create Today’s Spaces Page,” but because I had assigned it a relatively high estimate, I knew it would require more focus and time compared to smaller UI updates like the landing page. This helped me avoid leaving larger tasks until the last minute. Estimating also helped highlight which tasks were more complex than expected.

## Was tracking actual effort useful?
To be honest, I didn’t find tracking to be that useful during the actual development process. Most of the time, I would just work on tasks whenever I had free time, and stopping to record start and end times felt tedious and somewhat disruptive. For example, if I paused work on an issue and came back to it the next day, I had to remember to continue tracking from where I left off, which wasn’t always convenient and sometimes led to gaps or inconsistencies in my data. Because of this, tracking effort did not significantly influence my workflow while working on tasks. I was more focused on completing the implementation rather than monitoring how long each part took.

However, I can see how tracking effort is useful when looking back at the project as a whole. It provides a clearer picture of how much time was actually spent on different types of tasks, which can be helpful for evaluating both individual and team performance. For example, by reviewing the tracked data, it becomes easier to identify which tasks consistently took longer than expected, such as full page implementations compared to smaller UI components. Even though I didn’t actively use the tracked data while working, having that record allows me to better understand patterns in my workflow, such as underestimating debugging time or non-coding activities like planning and research. Overall, while I found the process of tracking effort somewhat tedious in practice, I recognize its value for reflection, accountability, and improving estimation accuracy over time.

## How did you track your actual effort?
I tracked coding effort primarily using the Google Timer, which I recorded the time spent actively coding. For non-coding effort, I used a combination of a timer and manual notes to record start and stop times for activities such as planning, researching, and debugging. I don't really know how accurate my times were since I'm kind of a person who takes breaks often inbetween tasks. However, non-coding effort tracking was less precise because it relied on manual input, and I may not have recorded every short activity. Despite this, I made an effort to log time consistently and avoid estimating after the fact.

# What would you change next time?
If I were to do this again, I would improve my tracking of non-coding effort by using a dedicated time-tracking tool more consistently instead of relying on manual notes. This would make the data more accurate and easier to manage. I would also break down larger issues into smaller subtasks before estimating. In the GitHub M1 task, we kinda just make 1 huge task for someone to do which created this unproportionate work load. Some of my estimates were inaccurate because the tasks were too broad, making it difficult to predict the actual effort required. Smaller, more clearly defined tasks would likely result in better estimates.

## Conclusion
Overall, effort estimation and tracking helped me better understand how I spend time during software development. While my estimates were often inaccurate, the process of comparing estimates to actual effort provided valuable insight that improved my planning and awareness throughout the project.
